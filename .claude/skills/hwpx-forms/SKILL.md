# 한글(hwpx) 양식 채우기 · 줄맞춤

공공기관 서류는 거의 한글입니다. 이 저장소에서 한글 파일을 여섯 번 만들며 매번 같은 함정에 빠졌고,
그 방법과 함정을 여기에 모았습니다. 도구는 `scripts/hwpx_tool.py` 하나입니다(표준 라이브러리만 사용).

```bash
T=.claude/skills/hwpx-forms/scripts/hwpx_tool.py
python3 $T 점검 보고서.hwpx                # 한글이 저장한 줄 그대로 — 낱말 가운데 끊김 · 짧은 끝줄 · 좁은 칸 갈림
python3 $T 맞춤 보고서.hwpx -o 새.hwpx --파랑 받은.hwpx   # 어절 단위 + 자간을 줄여 사각형으로 + 검사 + 파랑 판
python3 $T 맞춤 저장본.hwpx -o 새.hwpx --원본 처음.hwpx    # 한글에서 저장한 판을 한 번 더(이미 줄인 만큼은 뺌)
python3 $T 파랑 받은.hwpx 고친.hwpx -o 고친_파랑.hwpx       # 달라진 글자를 파랑으로(글을 손으로 고쳤을 때)
python3 $T 검사 원본.hwpx 새.hwpx          # 글자·표·그림·문단 수와 zip 차례가 그대로인지
python3 $T 읽기 보고서.hwpx                # 문단 글자를 차례대로(칸 안 줄바꿈 뒤 글자까지)
```

## 0. 고친 곳은 늘 파랑으로 보여 줍니다

사용자 — "앞으로는 이런식으로 수정을 하게 되면 수정 된 부분은 파랑색 글씨로 표시 해서 어떠한 부분이
수정이 되었는지 내가 확인 할 수 있도록 해주었으면 좋겠어"(2026-11-12). **사용자의 한글 문서를 고쳐
돌려줄 때는 언제나 두 판을 함께 보냅니다.**

| 판 | 무엇 |
|---|---|
| `…_파랑표시.hwpx` | 받은 판과 **달라진 글자를 파랑(#0000FF)** 으로 — 사용자가 보고 확인하는 판 |
| `…hwpx` (파랑 없음) | 같은 내용, 색은 그대로 — **내는 판**. 사용자가 파랑을 손으로 되돌릴 일이 없게 |

- 파랑으로 칠하는 것: 새로 넣거나 바꾼 글자, 자간·장평·크기·글꼴이 바뀐 글자(맞춤이 줄인 문단).
- 빈칸만 넣거나 지운 자리는 칠해도 안 보여 **앞뒤 한 글자씩** 칠합니다. 지운 글은 칠할 수 없어
  `파랑` 이 화면에 적으니 사용자에게 말로 알립니다.
- 받은 판(사용자가 마지막으로 준 파일)과 견줍니다. 사용자가 이미 해 둔 것은 칠하지 않습니다.
- 양식에 원래 파랑 글자가 있을 수 있습니다(붙임5 의 「□ 배경」 제목 등). 제목 말고 본문에도 파랑이 있으면
  다른 색(`--색`)을 쓰고 사용자에게 말합니다.
- 칠할 때 글자 모양만 복제해 바꿉니다. `검사`(글자·표·문단 수)가 파랑 판과 내는 판을 대조합니다.

## 1. 보고서가 완성되면 — 점검 → 맞춤 → 한글에서 확인

사용자는 줄이 낱말 가운데서 끊기면(「화학사/고」) 자간을 손으로 줄여 맞춰 왔습니다.
이 일을 없애는 것이 `맞춤` 입니다. 목표는 **문단이 사각형 모양**이 되는 것입니다(2026-11-11 사용자 —
"애매하게 둘·세 개 단어로 인해 두 줄로 늘어난 경우에도 자간을 줄여서 한 줄로 … 최대한 문장이 쓰여졌을 때
사각형의 모양을 갖추도록 해야 깔끔한 보고서가 되는 거거든").

1. **점검**: 사용자가 한글에서 저장한 파일이면 끊긴 곳이 정확히 나옵니다. 한글이 줄을 어디서 꺾었는지
   파일 안에 적어 두기 때문입니다.
2. **맞춤**이 하는 일 — 사용자가 손으로 하던 그대로입니다(아래 「사용자 예시」).
   - 모든 문단 모양을 **어절 단위**로 바꿉니다. 이제 한글이 빈칸에서만 줄을 꺾습니다.
     이것이 근본 해결이고, 글자 폭 어림과 상관없이 확실합니다(3절 ①).
   - 넘친 문단만 **자간을 줄여** 한 줄을 줄입니다. 원래 한 줄에 들어가는 문단은 건드리지 않습니다.
     - **자간은 줄이기만 합니다**(사용자 — "자간을 줄여서만 맞추는게 좋아").
     - **가장 적게** 줄인 값을 씁니다.
     - **원래 자간에서 −12%(바닥)까지** 줄입니다 — 원래 −6% 인 글자는 −18% 까지. 사용자가 한글에서 손으로
       줄인 값이 그랬습니다(2026-11-12 · 본문 0→−12, −6→−18 을 한 번에). 예전에는 「−12% 아래로는 안 내림」
       이라 원래 −5% 인 문단은 7%만 줄일 수 있어 덜 줄였습니다.
     - 한 번 맞춘 판을 다시 맞출 때는 `--원본 처음.hwpx` 를 줍니다. 처음 판의 자간을 「원래」로 세어 이미
       줄인 만큼을 빼고 남은 만큼만 더 줄입니다. 안 주면 받은 판의 자간이 원래가 되어 −12% 를 또 씁니다.
     - **머리(「  ○ 」「   - 」 같은 앞 빈칸 + 기호 + 빈칸)는 그대로** 둡니다. run 을 둘로 나눠 몸글만 줄입니다.
       머리까지 줄이면 기호 뒤 글이 시작하는 자리가 문단마다 달라져 오와 열이 어긋납니다.
     | 차례 | 경우 | 하는 일 |
     |---|---|---|
     | ⓪ | 좁은 칸에 한 낱말이 안 들어감(「화학물질안\|전원」) | 한 줄에 넣습니다. 어절 단위여도 한글이 글자로 꺾는 자리입니다 |
     | ㉠ | 끝줄이 남은 본문 문단(두세 낱말이 넘어감) | 끝줄을 윗줄로 올려 **줄을 하나 줄입니다** — 문단이 사각형이 됩니다 |
     | ㉡ | 양쪽 정렬에서 빈칸이 줄 폭의 10% 넘게 벌어짐 | 다음 낱말을 끌어올립니다 |
   - **끝줄이 짧은 문단만** 줄을 줄입니다 — 끝줄이 네 낱말 이하이거나 줄 폭의 1/3 이 안 될 때. 반 줄 넘게 찬
     끝줄은 사각형을 깨지 않는데, 그것까지 올리려면 문단 전체를 크게 줄여야 합니다(요약본 5→4줄에 −12 를 쓰려 했음).
   - 좁은 표 칸(한 줄에 한글 15자가 안 되는 칸)은 줄 수를 줄이지 않습니다.
     5자가 안 되는 칸(「Ⅰ / 개 / 요」처럼 세운 칸)은 아예 손대지 않습니다.
   - **얼마나 줄일지는 한글이 저장해 둔 줄 꺾임으로 문단마다 잽니다**(3절 ⑥).
     - 두 줄 넘게 저장된 문단은 어디서 꺾였는지가 그 글의 실제 폭 구간(실제 ÷ 어림)을 알려 줍니다.
       구간은 생각보다 넓습니다(가운데값 ±6%) — 꺾인 다음 낱말이 길면 넓어집니다.
     - 고를 때는 그 구간의 **넓은 쪽 3/4 자리**(`몫=0.75`)를 믿습니다. 가운데(1/2)로 골랐더니 한글에서
       17곳 가운데 8곳이 두 줄로 남아 사용자가 손으로 더 줄였습니다(2026-11-12). 덜 줄여 두 줄로 남으면
       사람이 다시 손봐야 하므로, 2~3% 더 줄이는 쪽을 택합니다.
     - 한 줄로 저장된 문단은 지금 들어간다는 뜻이라 손대지 않습니다. **어림이 저장된 줄 수보다 많이 세면
       저장된 줄 수를 믿습니다** — 이미 −12 로 줄여 3줄인 문단을 4줄로 세어 「4줄 → 3줄」로 헛되이 줄일 뻔했습니다.
     - 넓은 쪽으로는 바닥을 넘어야 하지만 가운데로 보면 바닥 안에서 되는 문단은 바닥까지 줄이고
       **「한글에서 한 줄인지 봐 주세요」** 를 붙여 알립니다. 가장 좁은 쪽까지 믿으면 안 될 문단까지 바닥으로
       줄여 글자만 빽빽해집니다(B 판 바닥 넷 가운데 셋이 그대로 두 줄).
   - **내어쓰기 확인**을 알립니다(3절 ⑫) — 줄 나눔·자간이 바뀌어 첫 줄 「(」 자리가 움직일 문단.
   - 바닥까지 줄여도 안 되는 곳은 그대로 두고 알립니다.
     - 「못 올린 짧은 끝줄」은 **글을 다듬어야 하는 곳**입니다.
     - ⓪ 의 남은 목록은 **칸 폭·글자 크기·글을 사람이 정해야 하는 곳**입니다.
   - 자간을 **넓히지는 않습니다.** 넓혀서 끝줄을 채우면 글자가 성겨 보입니다. 한때 넣었다가 사용자 말로 뺐습니다.
   - 글이 든 문단의 **줄배치 캐시를 지웁니다**. 그러면 한글이 열 때 줄을 다시 계산합니다(3절 ③).
3. **검사**는 맞춤이 끝나면 저절로 돕니다. 마지막 확인은 **사용자가 한글에서 여는 것**입니다.
   이 자리(리눅스)에는 한글이 없습니다. PDF 도 사용자가 한글에서 「PDF로 저장」 합니다.
4. **한글에서 열었는데 두 줄로 남은 문단이 있으면** — 한글에서 그대로 **저장만** 해서 다시 받아 `맞춤` 을
   한 번 더 돌립니다. 이번에는 한글이 실제로 그린 줄 꺾임을 읽으니 남은 문단만 정확히 더 줄입니다.

조절할 수 있는 값: `--바닥 -12 --여유 3 --끝줄 3 --빈칸 10 --원본 처음.hwpx --파랑 받은.hwpx`.
- 바닥을 올리면(예: `--바닥 -10`) 덜 빽빽하지만 못 올리는 끝줄이 늘어납니다.
- 여유는 저장된 줄 꺾임이 없는 문단에만 씁니다. 「글자가 어림보다 이만큼 넓어도 들어가게」라는 뜻입니다.
  기본 3% 는 본문 문단 3,169개의 배율 가운데값이 75% 자리에서 1.03 인 데서 왔습니다(넓은 쪽 3/4 와 같은 뜻).
- 빈칸 맞춤을 끄려면 `--빈칸 0` 입니다.
- 목록은 15개만 보이고 `--전부` 로 다 봅니다.

### 사용자 예시 (2026-11-11 · 「2030 국가 온실가스감축목표 부문별 조정안」 전·후 두 파일)

사용자가 직접 한글에서 맞춘 판입니다. 이 도구는 이것을 따라 하도록 맞췄습니다.

- 두 줄로 넘친 다섯 문단만 몸글 자간을 줄여 모두 한 줄로 만들었습니다. 원래 한 줄인 문단은 0 그대로입니다.
- 머리(「○ 」「- 」)는 0 그대로 두고 run 을 나눴습니다.
- 줄 나눔 기준은 「글자」 그대로였습니다. 전부 한 줄이 되어 차이가 없습니다.

| 문단 | 넘친 글 | 사용자 | 11-11 도구(가운데) | 11-12 도구(넓은 쪽 3/4) |
|---|---|---|---|---|
| ○ 2021년 수립된 … | 재조정 | −11 | −9 | −12 |
| - 총량 목표 … | 준수 | −5 | −6 | −9 |
| - 각 부문별 … | 조/정(낱말 가운데) | −2 | −2 | −3 |
| - 원료 수급 … | 완화 | −6 | −7 | −9 |
| - 부족분 800만 톤 … | 추가 분담 | −12 | −12(바닥 · 확인 요청) | 손대지 않음(짧은 끝줄로 알림) |
| - 건물, 수송 … | (한 줄) | 0 | 0 | 0 |

- **11-12 규칙은 이 예시에서 둘을 3~4% 더 줄이고 하나를 놓칩니다.** 대신 AI프런티어 붙임5 에서는 가운데로
  고른 값이 17곳 가운데 8곳 모자랐습니다(위 「사용자가 한글에서 더 고친 것」). 덜 줄여 사람이 다시 손보는
  쪽보다 조금 더 줄이는 쪽을 골랐습니다 — 사용자가 「완성되면 자간을 수동으로 바꾸는 일이 없도록」을 원해서입니다.
  너무 빽빽하다고 하면 `몫` 을 0.6 쪽으로 내리는 것을 먼저 검토하세요.
- 「부족분」은 바닥(−12)에서 실제로 한 줄이 됐는데 지금 모형(글자 폭 비례 · 빈칸 그대로)으로는 −12 로 모자라다고
  봅니다. 그 문단과 붙임5 「현장의 문제」(사용자가 −12/−18 로 줄인 3줄 문단)는 빈칸도 자간만큼 준다고 봐야
  설명됩니다 — 모형을 하나로 못 정한 부분입니다(3절 ⑥).
- 그 파일에서 사용자가 함께 한 것 가운데 **이 도구가 하지 않는 것**은 둘입니다.
  - 항목 사이 작은 빈 줄(5~6pt 빈 문단)
  - □ 머리 글꼴을 HY헤드라인M 굵게
  - 넣을지는 사용자에게 묻습니다.

### 사용자가 한글에서 더 고친 것 (2026-11-12 · AI프런티어 사례 붙임5 — 맞춤 B 판을 받아 검토한 v1)

| 고친 것 | 몇 곳 | 이 도구가 배운 것 |
|---|---|---|
| 두 줄로 남은 문단 자간을 1~3% 더 줄임 | 3 | 넓은 쪽(3/4)을 믿기 · 자간은 글자 폭 비례로 셈(3절 ⑥) |
| 본문을 원래보다 −12 씩 한 번에 (0→−12 · −6→−18) | 1 | 바닥은 「원래에서 −12」 |
| **내어쓰기를 다시 잡음**(○·- 항목 둘째 줄 시작 자리) | 13 | 3절 ⑫ — 알리기만 함 |
| 긴 문단을 뜻이 끊기는 자리에서 둘로 나눔(「…58명 응답」/「(’26.10.31. 기준) : …」) | 1 | 글을 다루는 일이라 도구가 하지 않음 |
| 한 항목만 「 - 」 앞에 빈칸 · 내어쓰기 따로 | 1 | 형제 항목과 「-」 자리가 다른지 사람이 봄 |

- 사용자가 다시 저장한 판에서 낱말 가운데 끊김은 **0** 이었습니다(어절 단위가 한글에서 그대로 먹음).
- 맞춤 B 판이 줄이려던 20곳 가운데 한글에서 실제로 한 줄이 준 것은 손대지 않은 17곳 기준 9곳이었습니다.
  지금 규칙(3/4 · 글자 폭 비례)으로 같은 파일(맞춤 전)을 다시 고르면 그 실패 여덟 가운데 여섯은 더 줄이고,
  바닥을 넘어야 하는 둘(−21 · −23 이 필요)은 아예 건드리지 않습니다. 대신 실제로 줄었던 아홉 가운데
  하나(「사고 대응 매뉴얼 …」 −12)는 이제 손대지 않습니다.

## 2. 양식을 채울 때의 차례

1. **주최 측·기관 양식 원본에서 시작합니다**(새로 짓지 않음). 문단 모양·글자 모양 번호는 양식의
   `header.xml` 에 있는 것만 씁니다. 바꿀 것은 안내 글(파란 ※ 글 등)뿐입니다.
   - 사용자 — "한글파일 양식이 있는데 왜 PDF 를 직접 만들었냐 … 주어진 파일을 그대로".
2. 칸을 찾을 때는 표 → 행 → 칸 → 문단 차례로 내려갑니다. 칸 이름(왼쪽 칸 글자)으로 찾으면 양식이
   조금 바뀌어도 맞습니다. 이 저장소의 `build/구동안내서_대조.py` 의 `hwpx_칸()` 이 그 예입니다.
3. 글을 넣은 뒤 **`맞춤`** 을 돌립니다.
4. **`검사`** 를 돌리고 쪽수 조건이 있으면 사용자에게 한글에서 쪽수를 봐 달라고 합니다. 저장된 줄배치로
   어림은 할 수 있지만 맞춤 뒤에는 캐시를 지웠으니 어림할 수 없습니다.
5. 공개 저장소에 올리기 전에 **문서 정보**를 봅니다(`Contents/content.hpf` 의 creator·lastsaveby).
   남이 준 파일에는 사람 이름이 들어 있을 수 있습니다.

남이 고친 판을 받았으면 **다시 짓지 말고 고칠 자리만 바꿉니다**(`build/구동안내서_최종본.py` 의 고침표).
틀린 것이 분명한 것만 고치고, 판단이 필요한 것은 사용자에게 묻습니다.

## 3. 꼭 지킬 것 — 실제로 겪은 함정

**① 줄 나눔 설정은 이름과 반대입니다.**
- `header.xml` 의 `<hh:breakSetting breakNonLatinWord="…">` 값의 뜻:
  - `BREAK_WORD` = **어절 단위**(빈칸에서만 꺾음)
  - `KEEP_WORD` = **글자 단위**(「화학사/고」)
- 근거(2026-11-11): **한글이 직접 저장한 원본 다섯 개**의 줄 꺾임을 셌습니다(빈칸이 있는 줄만).
  원본은 주최 측 양식 둘, 기관 원자료 둘, 팀원이 한글에서 저장한 파일 하나입니다.
  - BREAK_WORD 문단: 4,568번 꺾었고 낱말 가운데 끊김은 **0**
  - KEEP_WORD 문단: 3,408번 가운데 **681**(20%)
  - 우리 스크립트가 만든 파일은 뺐습니다. 줄배치 캐시를 우리가 적었으니 넣으면 제 답을 제가 맞히는 셈입니다.
- 한글의 기본값이 글자 단위라 양식 대부분이 KEEP_WORD 입니다. **이름만 보고 반대로 고치지 마세요.**
- 영어 쪽(`breakLatinWord`)은 확인할 근거가 모자라 건드리지 않습니다.
- **고정폭 빈칸**(`<hp:fwSpace/>` · Alt+Space)에서도 줄이 꺾입니다(원본에서 161번). 물질정보 문서는 빈칸을
  거의 다 이것으로 쳐 두었습니다. 처음에 이것을 글자로 봤다가 「칸이 좁다」 경고가 1,271개 나왔고, 고치니 17개가
  됐습니다. 폭은 0.15em 으로 어림합니다(어절 단위 줄 994개에서 86.6%).
- **묶음 빈칸**(`<hp:nbSpace/>`)은 한글 도움말대로 꺾지 않는 빈칸으로 봅니다. 이 저장소 문서에는 하나도 없어
  실제 줄로는 확인하지 못했습니다.

**② 칸 안 줄바꿈 뒤 글자는 tail 에 있습니다.**
- `<hp:t>앞<hp:lineBreak/>뒤</hp:t>` 에서 「뒤」는 lineBreak 요소의 tail 입니다. `t.text` 만 읽으면
  줄바꿈 뒤가 통째로 빠집니다. 팀원 문서를 대조할 때 「지운 줄」로 잘못 나왔습니다.
- 한글의 textpos 는 줄바꿈을 한 글자로 셉니다.

**③ 줄배치 캐시(`<hp:linesegarray>`)를 반쯤 남기지 않습니다.**
- 캐시는 「몇 번째 글자부터 · 세로 어디」입니다. 글을 바꿔 줄이 늘었는데 캐시가 모자라면 한글이
  **글자를 겹쳐** 그립니다(2026-09-14 사용자 지적).
- 두 가지 길이 있습니다.
  - **지우기**(맞춤의 기본): 한글이 열 때 다시 계산합니다. 공개 hwpx 스킬(Canine89/hwpxskill)의
    규칙이기도 합니다 — 「치환 후 hp:linesegarray 를 제거해 한글이 줄바꿈을 재계산하게 한다」.
  - **넉넉히 다시 쓰기**(`--캐시다시쓰기` · 이 저장소의 `make_hwpx.py` 계열이 써 온 방법):
    - 줄 수를 폭 3% 줄여 넉넉히 셉니다.
    - 세로 자리는 줄 간격만큼 늘리고, 뒤 문단을 그만큼 내립니다.
    - 둘째 줄부터 flags 는 1441792 입니다.
- **표·그림·도형이 든 문단(틀 문단)은 건드리지 않습니다.**

**④ 내어쓰기 문단은 둘째 줄부터 좁습니다.**
- 「○ 」 같은 머리 기호 문단이 내어쓰기입니다. 캐시의 horzsize 는 줄마다 같으니
  `<hc:intent>`(hp:switch 의 case 값 · HWPUNIT, default 는 그 두 배)를 직접 빼야 합니다.
- 이것을 빼먹었더니 폭 어림이 맞는 비율이 70% → 83% 로 갈렸습니다.

**⑤ 자간은 글자 모양에 있습니다.**
- 자간은 `<hh:charPr>` 안 `<hh:spacing hangul=… latin=…>` 이고, 글자 크기에 대한 %(−50~50)입니다.
  장평은 `<hh:ratio>` 입니다.
- 한 문단만 바꾸려면 글자 모양을 **복제해 새 번호**를 붙이고(`charProperties itemCnt` 도 하나 올림)
  그 문단의 run 만 새 번호로 바꿉니다. 원래 모양을 고치면 같은 모양을 쓰는 다른 문단이 다 바뀝니다.

**⑥ 글자 폭 어림은 ±3% 입니다.**
- 맑은 고딕 기준 값: 한글 0.98em · 빈칸 0.47em · 숫자 0.5em · 고정폭 빈칸 0.15em. 원본의 어절 단위 줄
  4,738개 가운데 **87.0%** 의 꺾는 자리를 정확히 맞히고, 어긋나도 대부분 3% 안입니다.
- **문단마다 다시 잽니다.** 한글이 저장한 그 문단의 줄 꺾임(「이 줄 글은 들어갔고 다음 글자는 안 들어갔다」)이
  실제 폭 ÷ 어림 폭의 구간을 줍니다(`배율구간()`).
  - 글자 단위로 꺾인 문단은 그 구간이 한 글자 폭(2~3%) 안쪽입니다. 우리가 글을 바꾸고 캐시를 둔 파일처럼
    꺾임이 글과 안 맞으면 버립니다.
  - 저장된 꺾임이 없으면 여유 3% 를 둡니다.
- **휴먼명조**는 맑은 고딕과 폭이 다릅니다(빈칸 0.60em). 사용자 예시의 다섯 값과 저장된 꺾임 26개로 맞췄습니다.
  기본값으로는 −8·−3·0·−2·−8 로 덜 줄여 셋이 두 줄로 남았습니다. 자료가 적으니 휴먼명조 파일을 더 받으면
  다시 맞추세요.
- 자간을 줄이면 **그 글자 폭에 비례해** 줄고 **빈칸은 그대로**라고 셉니다(`폭()` · 2026-11-12).
  - 근거: 같은 문단을 자간만 바꿔 한글이 두 번 저장한 줄 꺾임 19쌍(사용자 v1). 전·후 구간이 서로 어긋나지
    않는 모형이 이것뿐이었습니다(19/19). 글자 크기 비례(예전 모형)는 16/18 — 숫자·괄호·가운뎃점 같은
    좁은 글자도 한글만큼 준다고 셈해 덜 줄였습니다.
  - 한 번만 저장된 줄로는 모형들이 갈리지 않습니다(자간 섞인 문단 707개에서 96~97% 로 같음).
  - 글자 폭 비례에 빈칸도 준다고 보는 모형(18/19)과는 거의 같습니다. 덜 준다고 보는 쪽(빈칸 제외)을 씁니다 —
    덜 줄여 두 줄로 남는 것보다 1~2% 더 줄이는 쪽이 낫기 때문입니다.
- 문서에 한글이 저장한 줄이 200개 넘게 있으면 그 문서로 다시 맞춰 봅니다. 다만 기본값보다 나을 때만
  씁니다.

**⑦ zip 차례를 지킵니다.**
- `mimetype` 이 맨 앞이고 압축 없음이어야 한글이 엽니다. 나머지 파일은 바이트 그대로 둡니다.
- 칸 높이(`cellSz`)는 한글이 열 때 다시 잽니다. 손대지 않습니다.

**⑧ 한글로 열어 볼 수 없습니다.**
- LibreOffice 는 hwpx 를 못 엽니다. H2Orestart 확장으로도 정품 hwpx 를 못 열었습니다.
- 구조는 `검사` 가 봅니다(XML 짜임 · zip 차례 · 글자 · 표/칸/문단/그림/줄바꿈 수).
- 보이는 모양은 사용자가 봅니다. **"한글에서 열어 보세요"를 늘 끝에 적습니다.**

**⑨ 바이너리 hwp 는 읽기만 합니다.** `build/hwp읽기.py` 가 olefile 로 글자를 뽑습니다.

**⑩ 숫자·사실은 자료에서만 씁니다.** 양식을 채우다 모르는 값은 【입력 필요】로 남기고 사용자에게 묻습니다.

**⑪ 「· 」(가운뎃점 뒤 빈칸)를 함부로 지우지 않습니다.**
- 좁은 표 칸의 「지자체·환경청·해경· 소방·민간」 같은 빈칸은 작성자가 **줄을 꺾을 자리**로 넣은 것입니다.
  어절 단위 칸에서 한글이 바로 그 빈칸에서 꺾습니다(저장된 줄 꺾임으로 셋 다 확인).
- 띄어쓰기 오타로 보고 지웠더니 칸보다 긴 한 낱말이 되어 「해경·소|방」으로 갈렸습니다(2026-11-12 최종 검토).
  지우기 전에 `점검` 으로 그 자리에서 줄이 꺾이는지 보세요.
- 거꾸로, 좁은 칸에서 낱말이 갈린 곳(「구미·청주·오|창」 · 「환경청(공|단)」)은 같은 방법으로 고칩니다 —
  「구미·청주· 오창」 · 「환경청 (공단)」. `점검` 이 「칸이 좁아 한 낱말이 갈린 곳」으로 찾습니다.

**⑫ 내어쓰기는 첫 줄이 벌어진 만큼이 들어 있습니다 — 줄이 바뀌면 둘째 줄이 어긋납니다.**
- 「 ○ (현장의 문제) …」 같은 문단의 둘째 줄 시작 자리(`<hc:intent>`)는 작성자가 한글에서 첫 줄 「(」 앞에
  커서를 두고 잡은 값입니다(Shift+Tab). 같은 머리(「 ○ 」)인데 문단마다 2,844~3,136 으로 다릅니다 —
  양쪽 정렬로 첫 줄 빈칸이 벌어진 만큼 「(」 가 오른쪽으로 가 있기 때문입니다.
- 어절 단위로 바꾸거나 자간을 줄이면 첫 줄에 남는 폭이 바뀌어 「(」 가 움직이고, 둘째 줄과 어긋납니다.
  사용자가 맞춤 판을 받아 **열세 문단의 내어쓰기를 손으로 다시 잡았습니다**(2026-11-12).
- 한글 없이는 몇 HWPUNIT 까지 못 잽니다(어림 오차 ±300 — 사용자가 잡은 값과 견줘 봄). 그래서 고치지 않고
  `맞춤` 이 **「내어쓰기 확인」** 목록으로 알립니다(첫 줄 「(」 가 0.15글자 넘게 움직일 문단). 그 목록을
  사용자에게 보여 주고, 한글에서 「(」 앞에 커서를 두고 Shift+Tab 하면 된다고 말합니다.
