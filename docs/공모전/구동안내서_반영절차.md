> 2026-11-10 · 공모전 마감 전날. 사용자 — "그 팀원이 잡아준 방향성이 우리가 나아가야 할 방향이기 때문에
> 그 자료를 토대로 깃랩 자료를 다시 만들거야." **방향은 팀원 판을 따르고**, 숫자·화면 이름은 자료와 화면으로 확인합니다.
> 목표: 파일을 받은 때부터 GitLab 묶음 완성까지 **30분 안쪽**.

## 0. 받은 파일 두기 (1분)

- `docs/공모전/받은/` 에 둡니다. **저장소에 올라가지 않습니다**(`.gitignore`) — 이 저장소는 공개입니다.
- **한글 원본(.hwpx · .hwp)** 이 가장 정확합니다. PDF 만 오면 칸은 읽히지만 **띄어쓰기만 고친 것은 못 잡습니다.**

## 1. 무엇이 바뀌었나 — 대조 보고 (1분)

```bash
python3 build/구동안내서_대조.py docs/공모전/받은/<파일> --out release/구동안내서_대조.md
```

- 양식 [2-1] 일곱 칸을 칸마다 읽어 **우리 초안 대비 지운 줄 · 더한 줄 · 고친 줄**을 뽑습니다.
- 칸마다 **README 에서 맞출 자리**가 함께 나옵니다(아래 표).
- 숫자 대조(팀원 판에만 있는 숫자) · 공식 이름 · 흐름 개수(사용자 결정 3개 — 팀원 판) · 남은 【입력 필요】 · GitLab 주소.

## 2. 팀원 판의 화면 이름 대조 (3분)

```bash
node build/설명서_화면대조.mjs docs/공모전/받은/<파일>
```

- 휴대전화(아이폰 13)·PC(1366×768)로 도구 넷을 README 순서대로 끝까지 눌러 화면 글자를 모으고,
  문서의 「…」 낱말이 화면에 있는지 봅니다.
- **✗ 화면에 없음** 이 나오면 구동안내서 쪽 낱말이 화면과 다른 것입니다 → 사용자·팀원에게 그 목록을 그대로 전합니다
  (구동안내서는 메일로 내는 것이라 팀원이 고칩니다. 화면을 바꾸지 않습니다).

## 3. 사용자에게 한 번 보고 (2분)

- "팀원이 바꾼 방향 — ○○ · ○○ · ○○. README 를 이렇게 맞추겠습니다." 를 짧게.
- **숫자가 자료와 다르면 묻습니다**(지어내지 않음 · CLAUDE.md 2절 3항). 흐름이 3개(팀원 판)가 아니면 묻습니다.

## 4. README 고치기 (10~15분) — `docs/공모전/GitLab_README.md`

- 1의 「칸마다 팀원이 바꾼 것」을 위 표의 자리로 옮깁니다. **문장 결·강조점은 팀원 판을 따릅니다.**
- 지킬 것: 숫자는 `data/` · 검사 기록에서 · 화면 이름은 화면 그대로 · 흐름 3개(팀원 판) · 「위험·안전」 같은 단정 없음 ·
  구동안내서 파일은 묶음에 넣지 않음(메일 제출물 — `make_contest_package.py` 가 막음).
- 팀명·GitLab 주소가 나왔으면 `docs/공모전/참가정보.json` 에도 넣습니다.

## 4-1. 구동안내서 최종본 (1분)

```bash
python3 build/구동안내서_최종본.py                    # GitLab 주소가 정해지면 --gitlab 주소
```

- 팀원 판을 **다시 짓지 않고** 스크립트의 `고침표` 자리만 바꿉니다(틀린 것이 분명한 것만 — 지난 숫자 · 띄어쓰기).
- 결과물 `docs/공모전/[구동안내서]_기관명_팀명.hwpx` → 사용자가 한글에서 열어 쪽수·줄을 보고 「PDF로 저장」 → 메일.
- 팀원 판이 새로 오면 고침표의 앞 글이 안 맞아 멈춥니다 — 새 판에서 같은 자리를 다시 찾습니다.
